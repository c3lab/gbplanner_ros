# gbplanner_gz_sim

Gazebo Harmonic (gz-sim 8) simulation for the gbplanner ROS 2 stack: worlds, two
robot models, the `ros_gz_bridge` wiring and one launch file.

It exists to give the planner the four things it cannot run without -- odometry, a
lidar `sensor_msgs/PointCloud2`, TF and `/clock` -- and to move the robot along
the path the planner produces. The ROS 1 stack ran Gazebo Garden and Gazebo
Classic through `arl_gazebo_sim`; Jazzy pairs with Harmonic, so this half was
written rather than translated.

## Quick start

```bash
# Self-contained: no external assets.
ros2 launch gbplanner_gz_sim gz_sim.launch.py world:=cave_box

# The same world with the ground robot instead of the multicopter.
ros2 launch gbplanner_gz_sim gz_sim.launch.py \
    world:=cave_box robot_model:=marble_husky z:=0.5

# The DARPA SubT cave. Needs the subt_cave_sim models (see Assets).
ros2 launch gbplanner_gz_sim gz_sim.launch.py \
    world:=darpa_cave_01 x:=40.0 y:=5.0 z:=1.5 \
    resource_path:=/path/to/subt_cave_sim/models
```

`headless:=false` brings up the gz GUI; `rviz:=true` adds an RViz view of the
raw simulation (TF, point cloud, odometry, `/gbplanner_path`). That view's
topics are spelled for `rmf_owl`, so with another `robot_name` it comes up
empty - the scenario launch files in `gbplanner` pass `rviz:=false` and open
their own.

## Robots

`robot_model` picks one of `models/<name>/model.sdf.in` and, with it, the
follower that turns the planner's path into a velocity command. `robot_name`
defaults to the same string and is what every gz topic and TF frame is prefixed
with, so two robots of one kind differ only in that argument.

| `robot_model` | What | Driven by | Follower |
|---|---|---|---|
| `rmf_owl` | RMF-Owl multicopter, 1.46 kg, OS0-style lidar | `MulticopterVelocityControl` + a ROS position loop | `uav_path_follower_node` |
| `marble_husky` | MARBLE Husky, 46 kg skid-steer, OS0-style lidar | `DiffDrive` | `ugv_path_follower_node` |

The asymmetry is worth knowing: the UAV needs a ROS-side position loop only
because Harmonic dropped `MulticopterPositionControl` (see below). The UGV needs
nothing of the sort - every system its model uses ships with Harmonic - so its
follower is a path tracker and no more.

Only the multicopter has `/<robot>/enable`: `MulticopterVelocityControl` ignores
every Twist until something publishes `true` there, while `DiffDrive` acts on the
first one it gets.

## Worlds

| World | Needs assets | Notes |
|---|---|---|
| `cave_box` | no | primitives only, generated by `worlds/gen_cave_box.py`. Flat floor, so it drives as well as it flies, and it is what the verification runs against |
| `darpa_cave_01` | subt_cave_sim | DARPA SubT cave, 69 tile includes |
| `niosh_osrf` | subt_cave_sim | NIOSH experimental mine, one 223 MB DAE |
| `urban_circuit_01` | subt_cave_sim | SubT Urban Circuit, 34 tiles over three storeys |
| `cargo_hold` | subt_cave_sim | ship cargo tank, under 100 KB of meshes |
| `bwt_8_comp` | subt_cave_sim | eight-compartment ballast water tank, 102 KB |

`niosh_osrf`, `urban_circuit_01` and `bwt_8_comp` were ported from the Gazebo
Classic worlds in ROS 1's `arl_gazebo_sim/gzc/worlds`; `cargo_hold` came from
`gz/worlds`, where it was already gz-flavoured and only needed the ignition-era
plugin names updating. Each file's header
comment lists exactly what changed and why; the shape of it is always the same:
drop the Classic-only ROS bridge plugin, replace the ODE `<physics>` block, add
the Harmonic system plugins and a gz-gui block, and name the world after the
file rather than `default`.

## What it publishes

With the default `robot_name:=rmf_owl`:

| Topic | Type | Rate | Note |
|---|---|---|---|
| `/clock` | `rosgraph_msgs/Clock` | 1 kHz | one per physics step; set `use_sim_time` everywhere |
| `/rmf_owl/odometry` | `nav_msgs/Odometry` | 50 Hz | `world` -> `rmf_owl/base_link`, ground truth |
| `/rmf_owl/lidar/points` | `sensor_msgs/PointCloud2` | 10 Hz nominal | `frame_id: rmf_owl/laser_link`, 2048x128. 2048x128 rays per sweep is what the ROS 1 sim asked for and it does not keep up on a laptop GPU; measured 6-8 Hz. Lower it with `lidar_horizontal_samples:=` / `lidar_vertical_samples:=`. |
| `/rmf_owl/imu` | `sensor_msgs/Imu` | 200 Hz | |
| `/tf` | `tf2_msgs/TFMessage` | 50 Hz | `world` -> *world name* -> `rmf_owl` -> links |

and subscribes:

| Topic | Type | Note |
|---|---|---|
| `/gbplanner_path` | `nav_msgs/Path` | what `pci_general` publishes; the follower flies it |
| `/rmf_owl/command/velocity` | `geometry_msgs/Twist` | body frame, into gz |
| `/rmf_owl/enable` | `std_msgs/Bool` | arms the gz velocity controller |

`robot_name` is substituted into the model SDF, so it is simultaneously the gz
entity name, the prefix of every gz topic, the ROS namespace of the bridged
topics and the TF frame prefix. Two robots under one gz server differ only in
that argument.

## Joining it to `gbplanner`

`gz_sim.launch.py` is the include point. Its full argument list is in the
module docstring (`ros2 launch gbplanner_gz_sim gz_sim.launch.py --show-args`).
On the planner side, `gbplanner_node` needs:

```
remap  odometry        ->  /rmf_owl/odometry
remap  ~/pointcloud    ->  /rmf_owl/lidar/points     # node-private in ROS 2
param  use_sim_time    :=  true
```

`voxblox`'s `world_frame: world` and `PlanningParams.global_frame_id: world`
already match what this package publishes; nothing in `gbplanner/config` has to
change.

## Assets

Every world here except `cave_box` names models that are **not** in this
repository. They all come from one place, the `subt_cave_sim` package: 3.9 GB
behind git-lfs.

| World | What it needs from `subt_cave_sim` | Size |
|---|---|---|
| `darpa_cave_01` | 17 distinct `Cave ...` tile and artifact models, 69 includes | hundreds of MB |
| `niosh_osrf` | `niosh_seg01` | 223 MB in one DAE |
| `urban_circuit_01` | 12 `Urban ...` / `unit_box_*` / `Tunnel Tile Blocker` models, 34 includes | ~250 MB |
| `cargo_hold` | `cargo_hold_structure`, `bracket_toe`, `horiz_web_frame` | under 100 KB |
| `bwt_8_comp` | `bwt_8comp` | 102 KB |

Provide them in whichever way suits the deployment and point `resource_path:=`
(or `GZ_SIM_RESOURCE_PATH`) at the `models` directory:

* **bind mount** -- the ROS 1 checkout already has them:
  `-v /path/to/gbplanner_ros/bootstrap/sim/subt_cave_sim:/opt/subt_cave_sim:ro`,
  then `resource_path:=/opt/subt_cave_sim/models`;
* **vcs import** -- add the `subt_cave_sim` repository to a `.repos` file under
  `vcstool/` and `git lfs pull` it into `bootstrap/`;
* **Fuel** -- every tile is on `fuel.gazebosim.org` under the *OpenRobotics*
  owner. Rewriting the `<uri>`s to `https://fuel.gazebosim.org/1.0/
  OpenRobotics/models/Cave%20Straight%2001` lets gz download and cache them at
  first run (into `~/.gz/fuel`), at the cost of needing the network once.

None of that is required for `world:=cave_box`, which is built from primitives
and is what the package's own verification runs against. `make run-sim` mounts
the checkout named by `SUBT_CAVE_SIM` at `/opt/subt_cave_sim`, which is where
the scenario launch files look.

`models/rmf_owl/model.sdf.in` carries the flight dynamics of the original
RMF-Owl verbatim but replaces its 34 MB of DAE meshes with primitives; see the
comment at the top of that file for the rest of the deltas, including the one
that mattered: Harmonic has no `MulticopterPositionControl`.

## Why there is a `gbplanner_gz_control`

The ROS 1 SDF used two gz systems to fly: `MulticopterVelocityControl` (upstream)
and `MulticopterPositionControl` (an NTNU addition). Harmonic ships the first and
not the second, and its source is not available anywhere in this project:

```
$ find / -name "libgz-sim*multicopter*"
.../libgz-sim8-multicopter-control-system.so.8.11.0
.../libgz-sim8-multicopter-motor-model-system.so.8.11.0
```

Rather than fork a gz system, the position loop moved into ROS as
`gbplanner_gz_control/uav_path_follower_node`: the ROS 1 path follower plus a
saturated P controller that closes position onto the velocity command the
surviving gz system already accepts.

The UGV needed none of that. `DiffDrive` ships with Harmonic and takes the Twist
directly, so `ugv_path_follower_node` is only a tracker: it walks the planner's
path in the ground plane, steers on the bearing to the current waypoint, and
gives up forward speed while the robot is not pointing at it. That last part is
the whole difference between the two followers - a multicopter can be told to go
sideways and a differential drive cannot, so the position error becomes a
heading to turn to rather than a velocity vector to track.

## When the robot does not appear

`gz_sim.launch.py` waits for `/world/<name>/create` to show up in `gz service -l`
before spawning, because `ros_gz_sim create` calls that service once, does not
retry, and reports success even when Gazebo rejects the SDF. The wait is the
right shape but it has a failure mode of its own: gz-transport discovery runs
over the host network, and a gz server that was killed rather than shut down
leaves advertisements behind that make `gz service -l` return nothing for a
while. The launch then sits in the wait with Gazebo running and no robot in it,
and the only symptom is that `Entity creation successful` never appears in the
log while `gz topic -l` looks healthy.

If that happens, `make stop`, give it half a minute, and start again.

The other way a launch comes up looking like a dead simulator is not gz at all.
Every service runs with `ipc: host`, so Fast DDS's shared-memory segments live
in the host's `/dev/shm`; a container killed rather than shut down leaves them
there, and a few hundred of them stop ROS 2 discovery working inside the *next*
container. `ros2 topic list` then returns nothing while `gz topic -l` is fine,
`gbplanner_node` blocks forever waiting for `/clock`, and the control interface
prints `service planner_server is not available` until it is stopped. `make
stop` counts the leaked segments; `make clean-shm` removes them.

## Adding a world

Drop the `.sdf` in `worlds/` and rebuild this package. `--symlink-install`
symlinks the files that exist at build time, so a *new* file in an installed
directory is invisible until `colcon build --packages-select gbplanner_gz_sim`
runs again - editing an existing world needs no rebuild, adding one does. The
symptom of forgetting is `Unable to find or download file` from gz and nothing
else, because `gz sim` is being handed a path that is not there.

## Regenerating `cave_box.sdf`

`worlds/gen_cave_box.py` writes it. Change the geometry there and re-run:

```bash
python3 worlds/gen_cave_box.py
```
